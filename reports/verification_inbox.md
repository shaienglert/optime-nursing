# Verification Inbox Implementation

## Flow Implemented

1. Resident search creates UNKNOWN items
- Source: engine audit checklist generated by OPTIME matching.
- Location: [frontend/src/lib/optime-v2-engine.ts](frontend/src/lib/optime-v2-engine.ts)

2. UNKNOWN items become questions
- Implemented by `createVerificationInbox()`.
- Location: [frontend/src/lib/verification-inbox.ts](frontend/src/lib/verification-inbox.ts)

3. Questions appear in provider dashboard
- `createVerificationInbox()` returns provider-ready inbox records with facility_id, facility_name, and question list.
- Designed to be consumed by provider dashboard UI/API.

4. Provider answers update Facility Memory Engine
- Implemented by `applyProviderVerificationAnswers()` which calls `applyVerificationResponses(..., source: "PROVIDER_PORTAL")`.
- Memory engine then persists values with source/timestamp/expiry/confidence/count in runtime store.

5. Future searches use updated answers
- Existing capability assessment reads active memory before heuristic inference.
- Updated provider answers directly affect future matching decisions.

## Privacy Guarantee
- No resident information is shared in provider verification body.
- Updated request generation explicitly removes resident demographic/contact/budget/clinical-history summary and sends capability-only questions.
- Location: [frontend/src/lib/optime-v2-engine.ts](frontend/src/lib/optime-v2-engine.ts)

## New Module
- [frontend/src/lib/verification-inbox.ts](frontend/src/lib/verification-inbox.ts)

Exports:
- `createVerificationInbox(engineOutput)`
- `applyProviderVerificationAnswers(payload)`

## Notes
- The inbox module is implementation-ready for provider dashboard integration and API wrapping.
- It is intentionally capability-centric and resident-anonymous.
